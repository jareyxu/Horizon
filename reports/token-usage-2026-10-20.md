## 流程清单

旧版本只按提供商汇总，没有保留每次调用的 usage，因此无法追溯下列阶段
各自精确消耗多少 Token。这里不把推测写成实测百分比。

| 环节 | 本轮处理量 | 是否调用大模型 | 消耗来源及判断 |
| --- | --- | --- | --- |
| 标题初筛、评分与中文标题/摘要 | 71 条，每条至少一次逻辑调用 | 是 | 标题虽短，系统指令、个人偏好、六维评分规则、JSON 格式和发布分类说明仍逐条重复；每条还生成理由与评分维度。按调用规模看是主要嫌疑项，精确占比未知。 |
| 同题语义去重 | 1 次逻辑去重阶段，日报独立保留 | 是 | 输入入选候选的标题、摘要和标签；合并同一事件。此阶段候选池小，但历史 Token 未拆分。 |
| 入选后的扩写整理 | 7 条，每条至少一次逻辑调用 | 是 | 输入最多 4,000 字符正文、部分评论、搜索结果和长提示词；输出 20 余个中英文字段，包括背景、拍摄建议、适用人群等，是另一个主要嫌疑项。 |
| 模型内部推理 | 包含于各阶段调用 | 可能有 | 旧客户端只累计 completion_tokens，未单独保存 reasoning_tokens，不能判断 107,927 输出中有多少是推理。 |
| 播客长文预摘要 | 标题模式已跳过 | 本轮否 | 本轮此环节为 0。 |
| HTTP 抓取、来源核实、DuckDuckGo 搜索 | 常规采集及 7 条入选项核实 | 这些操作本身不调用大模型 | 操作本身不产生大模型 Token；搜索/正文被放入模型提示词时，其消耗归入扩写阶段。 |
| 页面排版、按分数排序、Tab 和原文折叠区 | 7 条精选、66 条未入选 | 否 | 本地模板渲染为 0；底部中文摘要的模型成本已计入第一阶段，不能把它算成额外调用。 |

“逻辑调用”不保证等于计费请求数：重试、解析失败后的翻译降级或提供商切换
可能增加请求；历史日志不能完整还原这些调用的 usage。

## 本次已实现的精简

1. 固定入选只影响是否入选，不再影响展示优先级；最终统一按真实评分降序。
2. 精选正文只保留中文标题、简短中文摘要和来源。移除入选规则、核验标签、
   人群、选题角度、拍摄建议、使用门槛、发布前核实、背景、参考链接和标签。
   固定入选规则、来源核实仍在后台执行。
3. 第二轮不再生成中英双语扩展分析，只请求 `title_zh`、`summary_zh`；
   不再为扩展背景额外搜索。保留已抓取正文和核实摘录来保证摘要有依据。
4. 第一轮也停止要求生成不再使用的人群分析、选题角度、标签和英文文本。
5. 生产页面删除“其他追踪推文”Tab，保留“全部未入选”和
   “其他 Follow Builders 资讯”。删 Tab 本身不节省模型 Token。
6. 新增异步隔离的阶段计量：标题/正文评分、语义去重、精选摘要、长文预处理、
   X 回复分析。记录提供商实际返回的输入、输出、已报告用量的请求数，以及
   接口提供时的推理 Token。推理 Token 是输出的子集，不重复加总。
   未提供推理明细的请求标为“未报告”，而不是推断为零。
7. 之后每轮用量独立保存到 `data/usage/horizon-日期-UTC时间戳.json`，
   不覆盖同一天的补跑数据；失败时也尽力保留已收到的 usage。

去掉生成任务才会减少模型工作量；只删页面展示没有这个效果。
实际节省量需要下一轮分阶段实测，不能预先承诺百分比。

## 下一步优化优先级（尚未实施）

1. 先查看新的分阶段账单，确认评分与扩写谁占大头。
2. 检查推理 Token 占比。若标题分类主要消耗在推理，可小样本验证非思考模式
   或限制思考预算，再比较入选准确度；本次没有擅自更改模型或思考模式。
3. 将标题分批评分，摊薄重复系统提示词；需测试漏项、JSON 解析和单批失败恢复。
4. 为相同 URL/标题和相同评分规则做缓存，避免同日补跑或重复来源再次评分。

硅基流动官方 API 说明提供 `enable_thinking`、`thinking_budget` 和
`usage.completion_tokens_details.reasoning_tokens`，但参数适用性需针对当前
模型核实。文档还说明 `max_tokens` 不含思维链，因此不能把降低这个参数当成
限制总输出成本的保证。

依据：[硅基流动 Chat Completions API](https://docs.siliconflow.cn/docs/api/chat-completions-post)。
